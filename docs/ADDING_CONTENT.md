# 内容维护指南

## 从一个链接开始

后续可以直接提供创作者主页、社区栏目、官方仓库、影片地址或具体作品链接。维护时先判断它属于 **信源** 还是 **作品**。

| 你提供的内容 | 更新位置 | 后续动作 |
| --- | --- | --- |
| 创作者主页、社区、电影节、仓库 | `data/sources.json` | 登记来源，挑选值得核对的具体作品 |
| 游戏、互动页面、影片或音乐作品 | `data/projects.json` | 找原作者和一手说明，补体验条件与证据 |
| 已有作品的新版本 | 原有作品记录 | 更新相应字段，追加 `timeline`，保持原有 ID |
| 失效、改名、收费变化或归属问题 | 原有作品记录 | 核对后更正，不以一次网络错误直接删除 |

## 1. 添加信源

推荐使用命令，避免漏字段和重复录入：

```bash
node scripts/add-source.mjs \
  --id source-slug \
  --name '信源名称' \
  --url 'https://creator.example.org/works' \
  --type creator \
  --language en \
  --scope interactive,game \
  --description '为什么这个来源值得持续查看'
```

请把示例网址换为真实来源。`type` 可用 `creator`、`platform`、`festival`、`repository`；`language` 可用 `zh`、`en`、`multi`。当前 `status` 固定为 `manual`，它表示来源已经登记、由编辑审阅，**不是自动采集状态**。脚本不会访问所提供的网站，也不会触发发布。

脚本要求公开 HTTPS 地址，拒绝凭据、IP 字面量、本地主机和非标准端口；相同 ID 或规范化后的 URL 不能重复。保存时使用独占锁和同目录临时文件进行原子替换。若任务异常中止导致 `data/.sources.lock` 残留，应先确认没有其他来源更新进程，再处理残留文件。

## 2. 添加作品

可以复制一条与作品类型接近的现有记录，替换全部字段。不要把旧条目的作者、证据、日期或体验状态一起复制过去。

| 字段 | 填写要求 |
| --- | --- |
| `id` | 稳定的小写 slug；改名也不必改变 ID |
| `title`、`subtitle`、`description` | 作品名称和简洁中文导读；不夸大完成度 |
| `category` | `interactive`、`game`、`film`、`music` 之一 |
| `creator` | 原作者名称与原作者页面 |
| `publishedAt` | 原作的完整发布日期；只有年份时填 `null`，另填 `year` |
| `addedAt` | 首次进入本站的日期，后续更新保留不变 |
| `lastReviewedAt` | 本次核对资料的日期 |
| `access` | 费用、账号、设备及 `play`／`watch`／`setup`／`demo` 模式；不清楚的条件填 `unknown` |
| `aiRole` | 只选择有依据的 `code`、`visual`、`audio`、`runtime`、`editing` |
| `tools` | 作者公开的模型与工具；未披露时保留空数组 |
| `links.primary` | 可体验或观看的原作入口；安装项目可以是其官方项目页 |
| `links.source` | 支持本条目身份与事实的一手来源 |
| `links.code`、`links.process` | 已公开的源码与流程；没有则为 `null` |
| `evidence` | 每条包含 `label`、`url`、`note`，说明来源支持哪项事实 |
| `verification` | 核验级别、具体范围和日期 |
| `why` | 一条具体推荐理由，避免仅写“震撼”“最强” |
| `firstStep` | 用户打开后第一步做什么 |
| `caveat` | 语言、设备、安装、模型成本等必要限制 |
| `timeline` | 依日期升序记录收录、公开更新或状态变化 |
| `collectionIds` | 合集 ID；同时更新合集中的作品列表 |

发布日期、收录日期、最近核验日期要分开。只有年份时，不要凭空补成 1 月 1 日。社交帖子热度如需记录，必须保留来源和快照时间，不能当作本站访问量。

### 核验等级

- `source-reviewed`：读过并核对了列出的公开来源。应说明所核对的是作者、AI 参与环节、公开入口或制作说明；不能写成本站已完整试玩。
- `hands-on`：进行了明确的实际体验。除 `note`、`checkedAt` 外，还须添加 `environment`，写清设备、浏览器、登录条件和测试范围；一次首页加载不代表全部功能正常。

初始内容采用第一种等级。HTTP 链接检查不提升核验等级。

### 合集维护

首版提供三个合集：

- `five-minutes`：可快速上手的作品。需要复杂安装或等待名单的作品不放进来。
- `made-with-ai`：有一手证据说明 AI 参与制作的作品；仅运行时调用 AI 的旧实验不自动进入这个合集。
- `open-source`：有公开代码入口的作品，详情中仍需说明许可证和环境要求。

一个作品可以属于多个合集。校验会检查作品与合集的双向引用，防止页面数量和实际内容不一致。

## 3. 验收并发布

```bash
npm run validate
npm run build
```

核对生成页面中的名称、来源、按钮目的地和筛选标签；检查手机与桌面布局。需要排查失效地址时，可运行：

```bash
npm run check:links -- --project <作品-id>
```

一次 `403`、`429`、地区限制或超时只说明本次检查受限。保留证据，人工确认后再更新条目。修改后的源码提交 GitHub，构建产物发布到网站托管服务；具体发布身份与地址由维护者管理。

## 用户提供新信源后的固定处理顺序

1. 核对网址和来源身份，检查是否已登记。
2. 登记来源、语言和关注范围。
3. 从中挑选有成品、有原作者、有 AI 参与证据的候选。
4. 为新作品建立档案；已有作品合并更新，避免重复。
5. 核对来源、体验条件和合集，执行校验与构建。
6. 发布后说明添加了哪些作品、哪些仍待核实。

不需要把信源接入和作品发布绑成一步；一个很好的来源也可能暂时没有符合收录标准的新作品。
